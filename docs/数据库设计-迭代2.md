## 2 表结构

### 2.1 `seller` 卖家账号

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | PK, AUTOINCREMENT | 主键 |
| `username` | TEXT | NOT NULL, UNIQUE | 登录名，种子为 `admin` |
| `password_hash` | TEXT | NOT NULL | `sha256(salt + 明文)` 的 64 位十六进制 |
| `salt` | TEXT | NOT NULL | 16 位十六进制（8 字节随机），改密时轮换 |
| `created_at` | INTEGER | NOT NULL | 创建时间，毫秒 |

**为什么密码不加密存明文、也不用 MD5**：明文落库等于泄露；MD5 不加盐时同密码同哈希，
彩虹表一查即破。加盐后每人哈希不同，彩虹表失效。

**为什么不是 BCrypt**：单账号系统，为它引入整套 Spring Security 不划算，
且需与迭代 1 保持「翻译式重写」的可对照性。**上生产必须换 BCrypt**，已在代码注释中标注。

### 2.2 `category` 分类字典（新增）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | PK, AUTOINCREMENT | 主键 |
| `name` | TEXT | NOT NULL, UNIQUE | 分类名，如「数码电子」 |
| `sort_no` | INTEGER | NOT NULL, DEFAULT 0 | 下拉框排序，越小越靠前 |
| `status` | TEXT | NOT NULL, DEFAULT 'enabled', CHECK in (enabled, disabled) | 禁用后不再出现在发布页下拉框 |
| `created_at` | INTEGER | NOT NULL | 毫秒 |
| `updated_at` | INTEGER | NOT NULL | 毫秒 |

**为什么用字典表而不是给 product 存分类字符串**：
① 改分类名只需改一行，不用扫全表；
② 避免「数码」「数码电子」「数码产品」这类同义异名；
③ 分类筛选可以走 `category_id` 索引，而不是字符串比较。

**`product.category_id` 允许为 NULL**：商品可以先不归类。
如果用 NOT NULL，就必须强制卖家发布时选分类，与「分类可后续维护」的体验冲突。

### 2.3 `product` 商品（多商品化）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | PK, AUTOINCREMENT | 主键 |
| `seller_id` | INTEGER | NOT NULL, FK → seller(id) | **归属卖家**，T2-10「仅见本人商品」的过滤依据 |
| `category_id` | INTEGER | FK → category(id)，可 NULL | 所属分类 |
| `name` | TEXT | NOT NULL | 商品名称，必填 |
| `description` | TEXT | NOT NULL, DEFAULT '' | 描述，可空串 |
| `image_path` | TEXT | NOT NULL, DEFAULT 'images/placeholder.png' | 相对路径；未上传时为占位图 |
| `price_cents` | INTEGER | NOT NULL, CHECK > 0 | 价格，**单位「分」** |
| `status` | TEXT | NOT NULL, DEFAULT 'on_sale' | `on_sale` / `delisted` / `frozen` |
| `published_at` | INTEGER | NOT NULL | 发布毫秒 |
| `updated_at` | INTEGER | NOT NULL | 最后修改毫秒（编辑、上下架都刷新） |
| `traded_at` | INTEGER | 可 NULL | 下架 / 成交毫秒 |
| `trade_result` | TEXT | CHECK in (success, failed, manual_delist)，可 NULL | 最终结果 |

**`status` 里为什么保留迭代 2 用不到的 `frozen`**：
迭代 3 要做「队首进入交易 → 自动冻结」，届时必须往这个字段写 `frozen`。
CHECK 约束在 SQLite 里改起来要重建表（SQLite 2.x/3.x 早期不支持 `ALTER COLUMN`），
**提前放开比事后迁移便宜得多**。迭代 2 代码不会写这个值，不影响验收。

**`price_cents` 为什么存「分」而不是 `REAL`**：
`9.90` 用浮点存会变成 `9.9000000000000004`，「必须两位小数」「必须 > 0」这类判断在边界上会误判。
存整数分彻底规避，展示时除以 100。

### 2.4 `intent` 购买意向

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | PK, AUTOINCREMENT | 主键，队列同毫秒时的兜底排序键 |
| `product_id` | INTEGER | NOT NULL, FK → product(id) | 所属商品 |
| `buyer_name` | TEXT | NOT NULL | 姓名，不校验格式 |
| `phone` | TEXT | NOT NULL | 电话，**不校验格式、不按号码去重** |
| `token_code` | TEXT | NOT NULL, UNIQUE | 32 位十六进制口令码 |
| `status` | TEXT | NOT NULL, DEFAULT 'pending' | `pending` / `trading` / `success` / `failed` / `cancelled` |
| `created_at` | INTEGER | NOT NULL | 提交毫秒，队列主排序键 |

**`phone` 为什么没有 UNIQUE**：
「同一号码重复提交互不干扰」是需求明文（清算 P1 遗留 C-3）。
加唯一约束会导致第二次提交直接报错，与需求相反。
如果担心重复提交刷队列，正确做法是在**业务层**做频控（本迭代不做）。

**`token_code` 为什么 UNIQUE**：
即使随机碰撞概率极低（128 bit），也要让数据库做最后一道保险——
碰撞时插入直接失败，不会出现「两个意向共用一个码、撤销时撤销错人」的事故。

**队列位次为什么不落库**：
位次 = `ORDER BY created_at, id` 的行号。
撤销一条，后面的自动前移，不需要批量 `UPDATE position`。
这既避免了「批量更新时中途失败导致位次错乱」，也免去了并发下的更新风暴。

## 3 索引设计

| 索引 | 定义 | 支撑的查询 | 对应任务 |
|------|------|-----------|---------|
| `idx_product_seller` | `product(seller_id, status)` | 我的商品列表（可按状态筛） | T2-10 |
| `idx_product_status` | `product(status, published_at)` | 买家列表「在售 + 按发布时间倒序」 | T2-11 |
| `idx_product_category` | `product(category_id, status)` | 分类筛选 | T2-11 |
| `idx_intent_queue` | `intent(product_id, status, created_at)` | 队列查询、取队首、递补 | T2-14 |
| `idx_intent_phone` | `intent(phone)` | 后台按号码核对历史提交 | 辅助 |

> 关键词搜索走 `LIKE '%kw%'`，**前缀不固定，普通索引无效**，只能全表扫。
> 课程演示的数据量（几百条）下可接受。若后续要优化，可上 SQLite FTS5 全文索引。

## 4 状态机（迭代 2 实际生效部分）

### 4.1 商品

```
           发布（多件可并存）
                 │
                 ▼
            ┌─────────┐   卖家下架（traded_at=now, trade_result=manual_delist）
            │ on_sale │ ────────────────────────────────┐
            └─────────┘                                 │
                 ▲                                        ▼
                 │                              ┌───────────┐
                 └──── 卖家重新上架 ────────────│ delisted  │
                     (traded_at=NULL,           └───────────┘
                      trade_result=NULL)              │
                                                      │ （迭代 3：成交）
                                                      ▼
                                                  再次下架
```

迭代 2 **只有** `on_sale ⇄ delisted` 这一条双向流转。
`frozen` 与「交易成功/失败」在迭代 3 接入。

### 4.2 意向

```
   提交 ──→ pending ──凭口令码撤销──→ cancelled
             │
             │ （迭代 3：卖家选定进入交易）
             ▼
          trading ──→ success / failed
```

迭代 2 **只有** `pending → cancelled` 一条流转，其余为迭代 3 预留。

## 5 事务与并发

| 场景 | 处理方式 | 依据 |
|------|---------|------|
| 多人同时提交意向 | SQLite 单写锁把写入串行化；`created_at` 在写入事务内取毫秒，同毫秒用自增 `id` 兜底 | NFR-03 |
| 连接池 | Hikari `maximum-pool-size=1` | 避免多个连接同时写导致 `SQLITE_BUSY` |
| 外键 | 每个连接 `PRAGMA foreign_keys = ON`（Hikari `connection-init-sql`） | 防止脏数据 |
| 日志模式 | `PRAGMA journal_mode = WAL`（写在 schema.sql，持久化到文件） | 读写不互相阻塞 |
| 改密 | `@Transactional`，验旧密码 + 写新哈希同一事务 | 避免半改状态 |

> **单连接池的代价**：并发读也会排队。课程演示级别（3~5 人同时点）完全够用，
> 数据量大时再换 MySQL/PostgreSQL，届时只需改 `spring.datasource` 与方言。

## 6 数据字典（种子数据）

| 表 | 主键 | 数据 | 用途 |
|----|:--:|------|------|
| `seller` | 1 | `admin` / `admin12345`（sha256+salt） | 默认登录账号 |
| `category` | 1~5 | 数码电子、图书教材、服饰鞋包、生活百货、运动户外 | 发布页下拉框、买家筛选 |

种子数据使用 `INSERT OR IGNORE`，**重复执行不会翻倍**。

**首次登录后必须改掉默认密码**，否则演示现场任何人都能登进后台。
改密后 `password_hash` 与 `salt` 都会变，`INSERT OR IGNORE` 因主键已存在不会再插入，
所以**重启应用不会把密码重置回 admin12345**。

## 7 从迭代 1 迁移

迭代 1（Python）的库与本迭代不兼容，两种处理方式：

### 方案 A：直接重建（推荐，迭代 1 数据均为演示数据）

1. 停应用；
2. 删除 `./data/shop.db`（以及可能存在的 `shop.db-wal` / `shop.db-shm`）；
3. 重启应用，`schema.sql` 自动建表并写入种子数据。

> 迭代 1 的数据库默认在系统临时目录（`%TEMP%/online_shop_mvp.db`），不在本工程内，
> 删除本工程的 `./data/shop.db` 不会影响迭代 1 原型。

### 方案 B：保留旧数据（若需要演示「历史商品」）

```sql
-- 在旧库上执行，逐步改造成新结构
ALTER TABLE seller ADD COLUMN created_at INTEGER NOT NULL DEFAULT 0;
ALTER TABLE product ADD COLUMN seller_id INTEGER NOT NULL DEFAULT 1;
ALTER TABLE product ADD COLUMN category_id INTEGER;
ALTER TABLE product ADD COLUMN updated_at INTEGER NOT NULL DEFAULT 0;
UPDATE product SET updated_at = published_at;
UPDATE product SET price_cents = CAST(ROUND(price * 100) AS INTEGER);  -- 旧字段为 REAL 时
ALTER TABLE intent RENAME COLUMN passcode TO token_code;
```

SQLite 的 `ALTER TABLE` 能力有限（不能改 CHECK、不能删列），
若旧表的 CHECK 里没有 `on_sale`/`delisted`，仍需重建表。
**方案 B 仅在没有「新建表 + 搬数据」的时间时才考虑。**
