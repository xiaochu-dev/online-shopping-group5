## 一、五个流转态与两条关闸线

```
                   商家确认          备货完成          开始发货          交易完成
   created  ──────▶  confirmed  ──────▶  prepared  ──────▶  shipped  ──────▶  completed
      │                  │                   │                  │
      └── 客户可取消 ─────┴───────────────────┘                  │
                                                        客户到此不可取消
      商家从 created 一直到 shipped 都可以取消（completed 之前）
```

| 状态值 | 页面文案 | 谁能推进 | 客户能否取消 | 商家能否取消 |
|---|---|:-:|:-:|:-:|
| `created` | 客户下单 | 商家 | ✔ | ✔ |
| `confirmed` | 商家确认 | 商家 | ✔ | ✔ |
| `prepared` | 备货完成 | 商家 | ✔ | ✔ |
| `shipped` | 开始发货 | 商家 | ✘ | ✔ |
| `completed` | 交易完成 | —（终局） | ✘ | ✘ |
| `cancelled` | 已取消 | —（终局） | ✘ | ✘ |

两条关闸线的差别是 B.1.2 与 B.1.3 的**唯一区别**：客户的关闸点在「开始发货」，商家的在「交易完成」。
因此 `shipped` 是唯一一个「客户不能取消、商家还能取消」的状态，测试必须单独钉住它。

## 二、取消是终局结果，不是第六个流转态

- `cancelled` 与 `completed` 平级，都是终局；
- **谁取消的记在 `cancelled_by`**（`buyer` / `seller`），不靠状态值区分——
  同一个 `cancelled`，客户看到的文案是「您已取消」，商家看到的是「商家已取消」；
- 新流程**不再产生 `failed`**：B 把「交易失败」并入「已取消」。
  `failed` 只作为迭代 1~3 的存量值存在，迁移时并入 `cancelled`。

## 三、非法流转与越权（都在 `OrderStatusService` 拦）

| 情况 | 处理 |
|---|---|
| 跳级（`created` 直接到 `shipped`） | 拒。目标状态由 `IntentStatus.next()` 算，调用方指定不了 |
| 倒退、终局后再推进 | 拒（`next()` 返回 null） |
| 非本单客户取消 | 按「订单不存在」处理，不暴露别人有没有这单 |
| 非本单商家推进/取消 | 同上（归属经 `product.seller_id` 校验，`intent` 表没有 seller_id） |
| 并发两次点击 | 条件 UPDATE `WHERE id=? AND status=<读到的状态>`，第二次 affected=0 → 提示「状态已变化」 |

## 四、取消要回补库存，但只回补「有明细」的单

B 的库存口径是**下单即扣、取消回补**（Q2）。所以取消必须在同一事务里把库存加回去，
否则单取消了、货却少了一件。

但迭代 1~3 的老意向单**从来没有扣过库存**。若无条件 +1，库存会凭空变多。
判断依据只有订单域知道：**这张单有 `order_item` 明细行，才说明它是走「下单扣库存」链路生成的**。

```
取消 → 查 order_item
        ├─ 没有明细（老意向单）→ 只改状态，不动库存
        └─ 有明细 → StockBatchPort.restore(orderId, 逐件数量)
                    ├─ 商品因库存归零自动下架 → 回补后恢复 on_sale
                    └─ 商家手工下架 → 保持下架（那是商家的明确意图）
```

## 五、两个跨域端口

| 端口 | 定义方 | 实现方 | 契约要点 |
|---|---|---|---|
| `cart.port.OrderCreatePort` | 购物车（胡） | 订单域（我，T4-06 待落地） | 现签名 `createOrder(buyerId, lines) → orderId` |
| `StockBatchPort` | 订单域 | 商品域（黄，T4-23） | `deduct()` 逐件、**不抛整单异常**；`restore()` 幂等、带回补 |

**一处待对齐（已列入群通知）**：`cart.port.OrderCreatePort` 现在只返回 `orderId`，
且注释写「任一不足则整单失败」；而澄清 Q3 的结论是**逐件拦截**——缺货那件提示、
其余照常下单、不拆单。T4-06 落地时，这个接口需要补一个返回
`orderId + 接单件 + 缺货件[]` 的结果对象，否则购物车无法把「哪几件没下成」告诉买家。

## 六、支付为什么被切断（T4-07）

迭代 3 的 `PaymentService` 会写 `intent.status = success`。B 删掉了 `success` 这个取值，
这条回写会在按支付的瞬间撞上 `status` 的 CHECK 约束，整笔事务回滚——表现是「支付按钮点了没反应」。

现在的口径（Q7）：**支付只写自己的支付单，一个字节都不碰订单状态，也不扣库存**
（库存在下单时已扣）。退款同理：只改支付单，订单是否结束由商家推进的状态机决定。

## 七、旧数据映射

| 旧值 | 新值 | 说明 |
|---|---|---|
| `pending` | `created` | 排队中 → 已下单待确认 |
| `trading` | `confirmed` | 交易中 → 商家已确认（备货信息不可考，不臆造成 `prepared`） |
| `success` | `completed` | — |
| `failed` | `cancelled` | B 把失败并入取消；`cancelled_by` 留 null（无法区分谁取消） |
