## 一、五个流转态与两条关闸线

```
                   商家确认          备货完成          开始发货          交易完成
   created  ──────▶  confirmed  ──────▶  prepared  ──────▶  shipped  ──────▶  completed
      │                  │                   │                  │
      └── 客户可取消 ─────┴───────────────────┘                  │
                                                        客户到此不可取消
      商家从 created 一直到 shipped 都可以取消（completed 之前）
```

| 状态值 | 页面文案 | 谁能推进 | 客户能否取消 | 商家能否取消 |
|---|---|:-:|:-:|:-:|
| `created` | 客户下单 | 商家 | ✔ | ✔ |
| `confirmed` | 商家确认 | 商家 | ✔ | ✔ |
| `prepared` | 备货完成 | 商家 | ✔ | ✔ |
| `shipped` | 开始发货 | 商家 | ✘ | ✔ |
| `completed` | 交易完成 | —（终局） | ✘ | ✘ |
| `cancelled` | 已取消 | —（终局） | ✘ | ✘ |

两条关闸线的差别是 B.1.2 与 B.1.3 的**唯一区别**：客户的关闸点在「开始发货」，商家的在「交易完成」。
因此 `shipped` 是唯一一个「客户不能取消、商家还能取消」的状态，测试必须单独钉住它。

## 二、取消是终局结果，不是第六个流转态

- `cancelled` 与 `completed` 平级，都是终局；
- **谁取消的记在 `cancelled_by`**（`buyer` / `seller`），不靠状态值区分——
  同一个 `cancelled`，客户看到的文案是「您已取消」，商家看到的是「商家已取消」；
- 新流程**不再产生 `failed`**：B 把「交易失败」并入「已取消」。
  `failed` 只作为迭代 1~3 的存量值存在，迁移时并入 `cancelled`。

## 三、非法流转与越权（都在 `OrderStatusService` 拦）

| 情况 | 处理 |
|---|---|
| 跳级（`created` 直接到 `shipped`） | 拒。目标状态由 `IntentStatus.next()` 算，调用方指定不了 |
| 倒退、终局后再推进 | 拒（`next()` 返回 null） |
| 非本单客户取消 | 按「订单不存在」处理，不暴露别人有没有这单 |
| 非本单商家推进/取消 | 同上（归属经 `product.seller_id` 校验，`intent` 表没有 seller_id） |
| 并发两次点击 | 条件 UPDATE `WHERE id=? AND status=<读到的状态>`，第二次 affected=0 → 提示「状态已变化」 |

## 四、取消要回补库存，但只回补「有明细」的单

B 的库存口径是**下单即扣、取消回补**（Q2）。所以取消必须在同一事务里把库存加回去，
否则单取消了、货却少了一件。

但迭代 1~3 的老意向单**从来没有扣过库存**。若无条件 +1，库存会凭空变多。
判断依据只有订单域知道：**这张单有 `order_item` 明细行，才说明它是走「下单扣库存」链路生成的**。

```
取消 → 查 order_item
        ├─ 没有明细（老意向单）→ 只改状态，不动库存
        └─ 有明细 → StockBatchPort.restore(orderId, 逐件数量)
                    ├─ 商品因库存归零自动下架 → 回补后恢复 on_sale
                    └─ 商家手工下架 → 保持下架（那是商家的明确意图）
```

## 五、两个跨域端口

| 端口 | 定义方 | 实现方 | 契约要点 |
|---|---|---|---|
| `cart.port.OrderCreatePort` | 购物车（胡） | 订单域（已落地：`OrderCreateProvider`） | `createOrder(buyerId, lines) → Result(orderId, orderNo, 接单件[], 缺货件[])` |
| `StockBatchPort` | 订单域 | 商品域（已落地：`StockBatchProvider`，黄可重写） | `deduct()` 逐件、**不抛整单异常**；`restore()` 以台账保证只回补一次 |

### 5.1 `OrderCreatePort` 的签名已改（2026-11-16）

原签名 `Long createOrder(...)` 只返回订单 id，注释写「任一不足则整单失败」。这与 Q3 的
**逐件拦截**冲突：只返回 id，购物车无从知道哪几件没下成，只能整车清空，把缺货件也一起抹掉。
现在返回结果对象：

```java
record Result(Long orderId, String orderNo,
              List<Long> acceptedProductIds, List<OrderCreatePort.Shortage> shortages)
```

购物车据此**只删接单件**、缺货件留在车里并标红（`CartService.checkout`）。
改动落在 `cart/port/OrderCreatePort.java`、`CartService`、`CartController` 三处，
已随本次提交一起改完并回归通过；接口语义变化已写进群通知。

### 5.2 下单主流程（T4-06）

```
merge(lines)  同商品数量合并（防止打 uq_order_item）
   ↓
逐件：商品存在？状态 on_sale？     否 → 记入 shortages（商品不存在 / 已下架）
   ↓
resolveAddress()  本次填的 > 买家默认地点 > 报错（A.2：订单不能没有交付地点）
   ↓
StockBatchPort.deduct(逐件)        条件 UPDATE stock >= ?，缺货件记入 shortages
   ↓
一件都没下成 → 抛异常（不建空订单）；否则
   ↓
INSERT intent（首件商品作 product_id、状态 created、快照姓名电话地址）
INSERT order_item（名称与单价 = 下单时刻快照）× N
UPDATE intent SET order_no = 'SO' + yyyyMMdd + 6 位 id
```

**为什么 `product_id` 只放首件**：这是迭代 1 留下的单值列（NOT NULL），完整明细在
`order_item`。因此 `OrderStatusService` 的商家归属校验改为「订单内任一件商品属于该卖家即可
操作整单」——否则多卖家合并下单时，第二个卖家永远推不动这张单，变成死单。

### 5.3 回补幂等落在台账上

`stock_restore(order_id PRIMARY KEY, restored_at)`：`INSERT OR IGNORE` 成功才继续回补。
不能靠 `intent.status` 判断——状态在同一事务里已经先改成 `cancelled` 了，第二次进入读到的
也是 `cancelled`，分不出「刚才是谁改的」。

## 六、支付为什么被切断（T4-07）

迭代 3 的 `PaymentService` 会写 `intent.status = success`。B 删掉了 `success` 这个取值，
这条回写会在按支付的瞬间撞上 `status` 的 CHECK 约束，整笔事务回滚——表现是「支付按钮点了没反应」。

现在的口径（Q7）：**支付只写自己的支付单，一个字节都不碰订单状态，也不扣库存**
（库存在下单时已扣）。退款同理：只改支付单，订单是否结束由商家推进的状态机决定。
