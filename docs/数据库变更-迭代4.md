## 一、`intent`：从「购买意向」升级为「订单头」

| 变更 | 内容 | 为什么 |
|---|---|---|
| `status` 取值 | 五态 `created / confirmed / prepared / shipped / completed` + 终局 `cancelled` | B.1.1 |
| ➕ `order_no` | 订单号，如 `SO202611160001`；存量单为 NULL | 页面展示与客服核对 |
| ➕ `cancelled_by` | `buyer` / `seller`，未取消为 NULL | 客户取消与商家取消的关闸点不同，文案与审计要分得开 |
| ➕ `cancelled_at` | 毫秒时间戳 | 同上 |
| ➖ 列语义停用 | `trade_result` / `fail_reason` 不再由新流程写；`fail_reason` 仍用于存取消原因 | 结果已由 `status` 表达 |
| ➖ 索引 `uq_intent_buyer_active` | **DROP** | 原约束「同一买家 + 同一商品最多 1 条未结束单」与 B 的多件下单、复购冲突 |
| ➖ 索引 `idx_intent_queue` | **DROP** | 队列机制随 B 整体退出 |

> `uq_intent_buyer_active` 必须用 `DROP INDEX IF EXISTS` 显式删：老库上它已经存在，
> 光在新脚本里「不创建」是删不掉的。

## 二、`order_item`：订单明细（新增）

```sql
CREATE TABLE order_item (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    intent_id    INTEGER NOT NULL REFERENCES intent (id) ON DELETE CASCADE,
    product_id   INTEGER NOT NULL,
    product_name TEXT    NOT NULL DEFAULT '',   -- 下单时快照
    price_cents  INTEGER NOT NULL DEFAULT 0,    -- 下单时快照
    quantity     INTEGER NOT NULL DEFAULT 1 CHECK (quantity > 0),
    created_at   INTEGER NOT NULL
);
CREATE UNIQUE INDEX uq_order_item ON order_item (intent_id, product_id);
CREATE INDEX idx_order_item_intent ON order_item (intent_id);
```

两个设计点：

1. **名称与价格存快照**。商品之后改名改价，历史订单不能跟着变；
2. **同单同商品只允许一行**。购物车里同一商品出现两次时合并数量，
   而不是产生两行——这也是「防重复点击」的第二道闸（第一道是应用层幂等）。

## 三、迁移：不能像 A 阶段那样删表重建

迭代 3 及以前 `intent` 里是**真实用户单据**，不能清空。SQLite 又没有 `ALTER ... MODIFY`，
所以只能走「建新表 → 拷数据（顺便翻译状态）→ 换名」：

```
1. CREATE TABLE intent_new (...)          -- 新的 CHECK 与新增列
2. INSERT INTO intent_new SELECT ..., CASE status ... END FROM intent
3. PRAGMA foreign_keys = OFF               -- 否则 order_item 的外键挡住 DROP
4. DROP TABLE intent
5. ALTER TABLE intent_new RENAME TO intent
6. PRAGMA legacy_alter_table = ON          -- 否则改名会把 order_item 的外键指到 intent_new
```

第 3 步与第 6 步是两个必须踩过才知道的坑，代码里已注释。迁移只在**检测到旧结构**时执行，
新库直接按新脚本建表，所以 `SchemaIdempotencyTest` 连跑三遍表结构不变。

迁移是**一次性的、幂等的**：`intent_new` 建完就换名，重复执行不会再触发。

## 四、支付表不动

`04-payment.sql` 本迭代零改动。支付与订单的关系被切成「两套独立状态机」：

- `payment.status`：`pending → paid → refunding → refunded`（自己走）；
- `intent.status`：五态由商家推进，**支付不写**。
